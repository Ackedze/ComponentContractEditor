# ComponentContract Editor — инструкция пользователя

## Обновлённый интерфейс — 0.2.102

Интерфейс стал компактнее и спокойнее: технические панели получили более явную
иерархию, preview — нейтральное рабочее полотно, а действия с semantic targets
собраны в одну строку. «Быстрая настройка» по умолчанию свёрнута. В форме
правила кнопки удаления и сохранения остаются доступны у нижнего края панели
при прокрутке. Редкие настройки границы и видимости цели свёрнуты в секцию
**Дополнительные настройки цели**. Постоянная нижняя техническая панель удалена.
Статус компиляции, ownership и просмотр read-only Compiled JSON доступны в
свёрнутой секции **Диагностика контракта** на вкладке **Проверка**. Контрактные
данные и логика проверки не изменились.

## Компактные уведомления — 0.2.98

Уведомления появляются как небольшие toast-карточки в правом верхнем углу. Они не участвуют в раскладке и не сдвигают рабочую область. Одновременно отображаются не более двух уведомлений, каждое занимает не более двух строк. Подробности проверки остаются в правом инспекторе.

## Уведомления без перекрытия — 0.2.97

Временные уведомления теперь появляются отдельной полосой под верхней панелью. Пока сообщение видно, рабочая область автоматически становится ниже: уведомление не перекрывает preview, результаты проверки и элементы управления.

## Проверка в правом инспекторе — 0.2.96

Вкладки называются **Каталог** и **Проверка**. На вкладке проверки сведения о
контракте, Product, режим, ожидаемые параметры, переходные состояния, результаты
и действия собраны в правом инспекторе; отдельная верхняя панель больше не
занимает высоту preview. Основные действия — **Проверить** и **Скачать отчёт**.
Отдельной проверки preview и действия «Взять выделение» больше нет.

## ButtonsGroup: ручное заполнение в 0.2.90

Существующие правила можно открывать и сохранять сразу после импорта, даже
если preview ещё не готов или цель не сопоставилась с текущим снимком. Save
использует targetId из правила; для изменения самой привязки используйте
«Перепривязать цель». Для нового правила сначала выберите слой в Anatomy.

Перед перезапуском сохраните незавершённое правило как Draft и экспортируйте
authoring ZIP. Перезапустите development-плагин и проверьте **0.2.90**. Механика группы общая
для компонентов; нормативный manual заполняется автором отдельно.

В 0.2.90 исправлено сопоставление восстановленной исходной иконки: локальные
Figma ID могут отличаться от независимого эталона при доказанной общей
библиотечной identity. Импортируйте существующий ZIP и экспортируйте заново,
чтобы compiled получил новый профиль. Правила, Reviewed и привязки менять не
нужно. Затем повторите проверку исходной dots-three-horizontal при
**Size=56 / Overflow=true / SingleIcon=True** у последней кнопки и сохраните
свежий validation report. Старый отчёт сохраняет прежний результат при replay;
новая сборка не делает отсутствие эталона доказанным соответствием.

В локальной сборке после исправления PARITY-014 смена View не должна создавать
`host-context-changed` из-за каталога неиспользуемой коллекции. Для приёмки
повторите Primary на второй позиции при Size=56 / Overflow=false, сохраните
свежий отчёт с полным capture и ожидаемым нарушением позиции, затем сделайте
чистый reset и повторите проверку. Новый capture содержит
`hostContextVariableModesVersion=1`; старый отчёт сохраняет прежний replay.
Менять правила или pins ради этого capture-исправления не требуется.
Живая приёмка исправления пока открыта.

Для запрета замены иконки у SingleIcon создайте constrained правило на корне
группы, только для слоя (`self`), свойство `composition.members`, тип ограничения
«Вложенный компонент / каталог иконки». В «Что проверять» выберите **«Сохранить
исходную иконку»**. В списке subjects выберите владельцев swap-порта внутри
четырёх semantic Button targets, а не сами glyph instances. Условие semantic
цели задайте через выбор **SingleIcon / VARIANT / True**; оно проверяет Button,
а путь subject указывает на его вложенный Addon. Отметьте **Icon-16, Icon-20 и
Icon-24** и оставьте Applicability → Variants → **«Все варианты»**. Запрет замены
иконки действует для всех размеров Button; эталон соответствует текущему варианту.
Порты выбираются из API превью и из объявлений точного закреплённого контракта
Button по совпадающему пути владельца. Порты только из закреплённого контракта
подписаны отдельно. Выбор не доказывает наличие порта в текущем превью и не
превращает декларации в наблюдённые факты. Сохранённые отсутствующие порты
также подписаны отдельно и сохраняются при редактировании.
Ключи иконок, `false` и таблицу соответствий вручную вводить не требуется.

Первую проверку можно выполнить на **Size=56 / Overflow=true**, сохранив норму
для всех размеров. Затем проверьте остальные размеры свежими отчётами.
Эталон берётся независимо для текущего библиотечного варианта;
замена компонента и его варианта дают
нарушение, а отсутствие доказанного эталона — неполную проверку. Существующий
архив не получает это правило автоматически: его создаёт и проверяет автор.

Чтобы различать правила одного типа, наведите указатель на карточку: рядом
появится полный **Rationale**. Подсказка также доступна при фокусе с клавиатуры.
Длинный текст можно прокручивать внутри подсказки; Escape закрывает её.
Клик по карточке открывает редактирование правила.

Над карточками есть поиск по **Rule ID**. Вставьте полный ID, чтобы получить
точное совпадение, или его часть, чтобы увидеть все подходящие правила.
Регистр букв не важен. Счётчик показывает число результатов; кнопка × или
Escape очищает поиск. При открытии правила и возврате к списку фильтр сохраняется;
загрузка другого компонента сбрасывает его.

Проверенный `current-contract-packages/ButtonsGroup.component-contract.zip` r56
содержит 17 Reviewed правил и четыре явно подтверждённые Button цели для
desktop Size=56 / Overflow=false и true. Для остальных размеров требуется
свежая проверка привязок и выполнения; all-variant норма сохраняется.

В 0.2.84 добавлена диагностика `dependency-reference-capture-failed`: новый отчёт
сохранит этап сбоя и текст ошибки Figma для каждой Button. Причина наблюдаемого
сбоя ещё не установлена. Повторите тот же тест SingleIcon=True у последней кнопки
при Overflow=false и выгрузите новый validation report. Ожидаемый host violation
сохраняется; отсутствующие дочерние эталоны остаются явной неполнотой. Перепривязка
целей и изменение правил для этой диагностики не нужны. Старый отчёт не получает
новую информацию при replay.


Разделы Execution, Нормативный владелец, Applicability и Typed constraint
сворачиваются по заголовку; заполненные значения видны в кратком описании и
сохраняются при переключении. Ошибка сохранения раскрывает нужный раздел.
Applicability изначально свёрнут при каждом создании или открытии правила;
его раскрытие в предыдущем правиле не переносится в следующее.

Для Figma Component Property выбирайте свойство из списка, затем отмечайте
одно или несколько значений. Тип известного свойства подставляется из API.
В коллекциях это работает для утверждения, фильтров и условий владельца/элемента;
тот же выбор доступен для variant property и typed subject conditions зависимости.
View показывает весь каталог закреплённого Button, поэтому можно отметить
Primary и Secondary вместе. Доступные варианты не становятся разрешёнными
автоматически: только отмеченные значения входят в правило.

У бинарного BOOLEAN доступны логические false/true; строковые VARIANT остаются
строками с исходным регистром. Если рядом со значением написано «сохранено,
отсутствует в доступном API», снимите его и выберите правильное значение.
Например, в требовании SingleIcon → Overflow снимите `True` и отметьте `true`.
Editor не меняет старое правило без вашего выбора. При отсутствии каталога
загрузите соответствующие факты или закреплённую зависимость; preview одного
варианта не подтверждает полный набор значений. Свободный TEXT и числовые
диапазоны по-прежнему вводятся вручную.

После обновления откройте прежний authoring ZIP и выгрузите новый ZIP из актуальной версии:
manual остаётся источником, compiler добавляет versioned root alias support.
Проверку инстанса запустите заново; старый report не заменяет свежий capture.

1. Получите свежий preview нужного D/M и Size/Overflow. Каждую встроенную
   Button свяжите с отдельной semantic role через явный remap. Если цели ещё нет,
   выберите Button в Anatomy и нажмите «Добавить цель выбранного слоя…».
   Действие регистрирует неподтверждённую цель и открывает сравнение: проверьте
   source address и явно подтвердите привязку; дополнительное правило для
   создания цели не требуется. При отмене цель остаётся unknown.
   Привязка относится
   к выбранному library variant и representation; другой вариант не наследует её
   по порядковому номеру. Не переименовывайте библиотечные слои ради identity.
2. В паспорте откройте «Прямые зависимости и состав», загрузите принятый Button
   authoring ZIP или read-only compiled JSON с полным Spinner closure. Source ZIP
   без compiled принимается через компиляцию reviewed source; existing compiled
   требует точного совпадения. Статус загрузки и ошибки видны в этом разделе.
   Выберите пакет, semantic target корня (его role может отличаться от `root`),
   четыре D / две M цели и соответствующую representation.
   «Добавить direct bindings» закрепляет revision и оба hashes. Сохраните паспорт.
3. Выберите root, создайте правило «С условиями», scope «Только слой» и тип
   «Состав и условия коллекции». В группе «Одно свойство»
   выберите «Состав коллекции» (`composition.members`): поиск понимает
   «состав» и «коллекция», свойство не требует Observed fact. Корневая role может называться `buttons-group`:
   Editor проверяет явный root anchor; переименование в `root` не нужно.
   Состав можно заполнить из direct bindings;
   выберите нужные members/representations и операцию. Читаемое описание под
   формой показывает сохраняемый смысл. Для D/M с разным составом задайте
   отдельные ограничения с явным representation scope.

| Норма | Настройка формы коллекции |
| --- | --- |
| Только встроенные экземпляры | «Закрытый состав»; включает скрытые, без property gate |
| Видимые D 1–4 / M 1–2 | «Количество», только effectively visible, min 1 и max 4/2 |
| Primary необязателен, максимум один | Фильтр View, VARIANT, `Primary`; количество max 1 |
| Primary первый видимый | Тот же фильтр; позиция «Первый» |
| Только Primary/Secondary | Дочернее свойство View, VARIANT; отметить Primary и Secondary |
| Size равен Size группы | Mapping Size VARIANT → Size VARIANT владельца, без преобразования |
| SingleIcon максимум один, последний | Фильтр SingleIcon VARIANT `True`; max 1 и позиция «Последний» |
| SingleIcon требует Overflow | Фильтр SingleIcon `True`; «Выбранные элементы требуют значения владельца»: Overflow VARIANT `true` |
| SingleIcon требует две кнопки | Количество всех видимых min 2; «Применять, когда есть элемент» SingleIcon VARIANT `True` |
| Overflow=true требует две кнопки | Количество всех видимых min 2; host условие Overflow VARIANT `true` |

`Overflow` у root имеет строки `false`/`true`; `SingleIcon` у Button — строки
`False`/`True`. BOOLEAN `true` не заменяет VARIANT `True`. Формы сохраняют регистр
и проверяют типы. Отсутствие Primary или видимого SingleIcon допустимо; SingleIcon
при Overflow=false проверяется как требование и даёт нарушение.

Для fixed SingleIcon icon используйте существующий тип «Вложенный компонент /
каталог иконки»: выберите доказанную semantic цель и relative instance/port,
добавьте typed условие SingleIcon VARIANT `True` на semantic цель. Domain иконки
заполняйте по независимому readback каждого нужного Size. Обычные addons остаются
в Button scope. Выбор subject и typed условия не требует массива JSON.

Root layout baseline задавайте точечно: HORIZONTAL, gap и четыре padding.
По решению владельца при ручном заполнении 02.10.2026 правило 5 защищает весь
визуальный образ корня: группа «Внешний вид», fill/opacity/radius/effects,
Permission «Запрещено», scope «Только выбранный слой», Variants «Все».
`appearance.stroke` уже защищён отдельным правилом со всеми ограничениями
обводки; повторно добавлять его в визуальную группу не требуется.
Состав `visual-style@1` фиксирован: другие применимые визуальные атрибуты
задавайте отдельными явными правилами. Отменённые root Hug/Hug и width/height
в нормы группы не добавляйте. Action/menu/code нормы сохраняйте в отдельных
context/delegated routes, пока нужные входы не подключены.

Скрытие middle допустимо: membership продолжает проверять исходный экземпляр,
а child execution становится inactive. Missing identity, visibility, order,
property или pin показывается как неполнота; известное нарушение другого member
сохраняется. Save/session reopen и ZIP сохраняют точные source rules/bindings/pins.
Чтение новых форматов в локальном Apollo v4 проверено; published release/Proxy
и live negative/reset нового manual принимаются отдельно в бэклоге.

## Проверка открытого SLOT (0.2.71)

Перезапустите development-плагин, убедитесь в версии **0.2.71**, импортируйте
актуальный ручной ZIP и снова нажмите «Проверить».
Новое поле в manual заполнять не нужно. Если правила допускают ограниченный
захват, Editor проверяет host и подтверждённую границу SLOT, не обходя внешнее
содержимое. Внизу и в JSON это явно указано — внутренние компоненты содержимого
не получили автоматическую проверку своих контрактов.

Если правило требует фактов содержимого, собственный SLOT-якорь неоднозначен
или независимый reference неполон, граница не используется для пропуска.
Повторные/циклические API ID дают «Не выполнено» с конкретной причиной.
Не повышайте лимит и не меняйте правила ради зелёного статуса.
Изменение manual после захвата отменяет пригодность старого ограниченного
снимка: требуется новая проверка выбранного instance.

## Открытый native SLOT (0.2.70)

После живого preview выберите настоящий SLOT в Anatomy. Создайте правило
свойства слоя **Содержимое слота** (`composition.content`), Permission
**Разрешено**, область **Только выбранный слой**, путь управления **Slot**.
Точный Figma property ID подставится в поле якоря из `slotContentId`.
Не заменяйте его названием Body. Пустой target означает выбранную цель;
пустой owner target — корневой компонент. Для вложенного владельца нужно
явно указать его target ID.

Выберите **Внешнее: проверять только границу слота**, заполните rationale,
владельца правила и сохраните reviewed. Содержимое может быть произвольной
композицией. Сам слот не становится внешним; эта policy не разрешает менять
все свойства его layout и не проверяет содержимое по чужому контракту.
Для recursive baseline-правил граница должна быть явно
`component-owned@1`; правила без этой границы не переписываются автоматически.

Без доказанного якоря/владельца/эталона проверка неполная, а не зелёная.
Правило не задаёт обязательность заполнения, допустимость placeholder или
конкретный набор дочерних компонентов — это отдельные решения автора.

## Допустимые modes коллекции (0.2.68)

Откройте живой preview, выберите нужный слой и создайте правило свойства слоя
`Mode · <название коллекции>`. Для «С условиями» и `propertyDomain` редактор
показывает именованный множественный выбор допустимых modes. Для
`propertyExclusion` отмечаются запрещённые modes. Сохраняются key коллекции и
mode IDs, а не локальный collection ID или названия.

Это ограничение значения свойства. Поле Modes в области действия — другое:
оно определяет, когда правило исполняется. Для проверки допустимого набора
обычно оставьте **Modes = Все**, иначе запрещённое состояние может исключиться
из проверки. Заполните rationale и нормативного владельца до `reviewed`.
При отсутствии доказанного resolved mode проверка неполная; цвет и default
коллекции не заменяют этот факт. Новое правило добавляет автор вручную.

## Высота относительно line-height (0.2.63)

Для правила слоя выберите `bounds.height`, Typed constraint «Layout» и оператор
«Не больше эталонного line-height». Укажите semantic role эталонного TEXT,
например `major-text`. Роль должна однозначно разрешаться в контракте.
Не задавайте одновременно фиксированные min/max/value. Применимость к видимому
Addon задаётся отдельно через объявленный semantic API `addonVisible`.
Editor сравнивает с доказанным line-height выбранного варианта библиотеки,
не с вручную изменённой типографикой. Неизвестный/AUTO reference не считается успехом.

## Владелец вложенного слота (0.2.62)

В Control path типа «Слот» поле «Владелец свойства слота» принимает локальный
target ID, например `target.amount`. Оно означает, что указанный BOOLEAN-якорь
принадлежит этому вложенному компоненту, а не корню. Пусто = прежний корневой слот.
Владелец должен непосредственно содержать слот в каждом Figma-представлении.
Это часть manual-контракта, а не обход ограничений: допустимые семейства проверяются
обычными constraints. Содержимое внешнего слота не наследует эталон placeholder.

## Текстовые цели при смене вложенного варианта (0.2.61)

В паспорте контракта есть одноимённое поле со списком связей:
`[{"targetId":"target.minor-text","anchorTargetId":"target.minor"}]`.
Оно нужно, когда TEXT остаётся той же смысловой частью внутри другого варианта
вложенного компонента. Указываются существующие target ID, не имена Figma-слоёв.
Редактор сохраняет `variantContinuity` в manual; compiled вычисляется заново.
Изменение связей возвращает зависимые правила в draft для повторного review.
Пустой список отключает связи. Это не разрешает swap, изменение стиля или opacity.
Без доказанной принадлежности семейству и независимого библиотечного образца
сопоставление остаётся неизвестным — проверка не объявляется успешной.

Эта инструкция относится к экспериментальному MVP. Плагин редактирует ручной
слой контракта одного компонента и автоматически создаёт исполняемый артефакт
для Apollo.

3. Верните `SingleIcon=False` и проверьте снова: прежняя анатомия и проверки
   вернулись; manual source не изменился от переключения вариантов.
4. Повторите для `[M] Button` и inverted-представлений, если они доступны.

«Элемент или свойство недоступны» означает подтверждённую неприменимость,
а не нарушение. Неизвестная структура, расхождение с каталогом или усечённый
снимок по-прежнему дают неполную проверку. Не создавайте искусственно невозможные
состояния ради теста: негативный сценарий выбирается из доступных настроек.

Скачайте отчёты. Другие правила могут давать свои нарушения; проверяйте Rule ID
`component:web-core.button.single-icon-content-shape.*`. Источник пока Draft,
Editor исполняет его в тестовом режиме и отмечает это в отчёте.

В форме правила теперь отдельно видны **Источник variant/context условий**,
**Semantic API условия**, **Fact выбранного ограничения**, остальные ограничения
и control paths. Ограничения выбираются в форме или задаются JSON-массивом и выполняются
совместно (AND), а не теряются при сохранении. Для условий вложенного слоя можно
явно выбрать корень компонента. Старые правила автоматически не переосмысляются.

Все пробелы пакета ещё не закрыты: доступность опирается на текущие Athena facts
и свежий reference. Сложные swaps, новые структуры, exposed properties и полный
граф зависимостей требуют отдельной поддержки; Loading и внешние правила не активированы.

### Готовность контракта и полнота сценария — 0.2.15

В интерфейсе есть два независимых показателя: готовность контракта показывается
в нижней панели **Каталога**, а полнота выбранного сценария — в правом инспекторе
**Проверки**:

- **Контракт: Draft** — готовность всего пакета, включая неисполняемые правила,
  непроверенные делегации, authoring-ошибки и несопоставленные цели.
- **Этот сценарий** — полнота проверки выбранного инстанса. Например, мобильное
  правило не ухудшает полноту desktop-проверки, если платформа известна.

«Проверка завершена» не означает отсутствие нарушений и не делает весь контракт
Ready. Неизвестная применимость остаётся непроверенной; отсутствие слоя само по
себе не доказывает неприменимость правила.

В «Не выполнено» перечислены именно отсутствующие данные и отдельно **Уже
доступны**. Если данные есть, но `context-only` ещё не подключён к автоматической
проверке, это указано прямо. Для «Не применяется» показано конкретное отличие
контекста или невыполненное условие. Неизвестные Product ID требуют сопоставления:
Editor не переименовывает их автоматически.

Скачанный JSON содержит `summary.contractReadiness` и
`summary.scenarioCoverage`. Исходные результаты Predicate Engine сохранены в
`results.engine`, а дополнительные объяснения — в `results.editor`.
Достаточно перезапустить Editor 0.2.15 и повторить проверку с текущим manual;
переимпортировать старый ZIP поверх сессионных изменений не нужно.

### Токены и Hint — 0.2.14

  **Полный JSON** раскрывает исходные данные без обрезания. Если привязки нет

- Отдельное универсальное правило: при включённом Hint допустим Size 56, 64
  или 72. Оно проверяется по явным bindings `semanticApi.hintVisible/size`.

- Для приёмки перезапустите Editor **0.2.14**, загрузите обновлённый

  и другом Product. В другом Product сравните Size=48 и Size=56 при Hint=true.

### Скачать отчёт проверки — 0.2.13

1. Откройте вкладку **Проверка**, выберите Product и выполните проверку.
2. В правой панели нажмите **Скачать отчёт**. Кнопка доступна и при результате
   «Проверка неполная».
3. Передайте файл `button.validation-report.<дата>.json` для разбора.

Он содержит Product, modes и факты проверенного инстанса, baseline, Figma ID,
ревизию manual source, сами правила, ошибки компиляции, результаты и конкретные
причины «Не выполнено». Временное включение Draft для Editor отмечается отдельно.
Ссылка на временный preview может уже не открываться; снимок остаётся в отчёте.

После смены Product, изменения сохранённого контракта или нового запуска старый
отчёт сбрасывается: сначала повторите проверку. Экспорт фиксирует сохранённую
manual-ревизию на момент исполнения, а не несохранённые поля формы.

**Файл содержит названия, тексты и свойства слоёв, а также ручные правила.**
Изображения не включаются, автоматической отправки нет. Это отдельный отчёт
проверки макета: `validation-report.json` внутри ZIP описывает только корректность
компиляции контракта и не заменяет его.

### Сохранение и полнота проверки — 0.2.12

- При сохранении `reviewed` проверяются обязательные поля и корректность правила.
  Пустое Rationale и другие ошибки подсвечиваются; фокус переходит к первому
  полю. Ошибочное изменение не заменяет сохранённое правило. Незавершённое
  правило можно сохранить как Draft.
- В результатах **«Не выполнено»** показывает исключённые компилятором правила
  с причинами, недостающие runtime-факты, непроверенные внешние делегации и
  отсутствующие результаты исполнения. Это не нарушения макета.
- **«Не применяется»** означает установленное несовпадение условий сценария,
  а не ошибку исполнения. Policy-only разрешения не требуют проверки.
- При пропущенных правилах, неопределённых результатах или ошибках источника
  показывается **«Проверка неполная»**. Исключённые правила показываются для
  всего пакета: редактор не считает их неприменимыми без доказательства.
  «Проверка завершена» не означает отсутствие нарушений или готовность каталога
  к публикации. Изменение manual source очищает устаревшие результаты.

Проверка обновления: откройте reviewed-правило Hint, очистите Rationale и нажмите
«Сохранить правило». Поле должно подсветиться, правило — остаться неизменным.
Заполните обоснование и сохраните. При проверке Button-пакета откройте категорию
«Не выполнено»: у каждой записи должна быть причина, без фиктивного сравнения
«Сейчас → Должно быть».

В редакторе автор описывает:

- стабильный component ID, назначение и границы применения;
- Figma/code representations и единый semantic API между ними;
- ссылки на документацию, примеры, решения и профили генерации;

- какую часть компонента регулирует правило;
- какое свойство или группу свойств оно охватывает;
- разрешено ли изменение;
- через какой публичный путь им можно управлять;
- какие ограничения действуют;
- для каких variants и modes применяется правило;
- severity, rationale, owner и remediation intent.
- отдельный execution route: predicate, policy-only, delegated или context-only.

Пользователь не редактирует RuleIR, coverage, runtime policy и compiled JSON.
Эти части создаются компилятором.

Основная формула правила:

```text
semantic target
  → capability
  → permission
  → control path
  → typed constraint
  → applicability
  → execution route
```

## 2. Что импортировать

В версии 0.2.11 неизвестный Product/Channel — это недостаток данных, а не
«Не применяется». Известный другой Product означает неприменимость только
конкретного правила, а не разрешение компонента всеми остальными правилами.

Если у правила стоит `scopeStatus: needs-confirmation`, подтвердите область
действия в редакторе перед включением predicate-проверки. Условия из
`applicability.context` пока требуют отдельного runtime-сопоставления:
компилятор сохраняет их, но блокирует исполнение вместо потери условия.
Ручные поля не исправляются автоматически.

Для первой сессии используйте один компонентный Athena-пакет.

### Button

```text
shared/design-system_ab/JSONS/web/components/web-core/core/Button/
```

### CorporateContent

```text
shared/design-system_ab/JSONS/web/components/web-corp/CorporateContent/
```

Нажмите **Загрузить пакет** и выберите все JSON-файлы внутри нужного каталога.
После загрузки действие **Загрузить пакет** остаётся в шапке,
поэтому для смены компонента не нужно перезапускать Editor. Также
можно передать ZIP, содержащий эти JSON-файлы.

Рекомендуемый состав пакета:

- `contract.generated.json`;
- `contract.overrides.json`;
- `semantic-targets.json`;
- `composition-contract.json`;
- `rules.json`;
- `examples.json`;
- `audit-mapping.json`;
- `agent-context.json`.

Не загружайте большой raw-файл `Web _ Core -- Button.json` или
`Web _ Corp Components -- CorporateContent.json`. Это источник Athena, а не
рабочий файл Editor.

Импорт существующего `component-contract.v2.json` поддерживается, но такой файл
считается только read-only evidence. Из compiled JSON нельзя достоверно
восстановить утраченное авторское намерение.

## 3. Устройство окна

### Верхняя строка — режим работы

Вместо логотипа и названия в верхней строке находится segmented control:

- **Каталог** — паспорт, anatomy, semantic targets и manual rules;
- **Проверка** — запуск Predicate Engine для выделенного экземпляра.

В режиме проверки необходимо выбрать **Product** из канонического списка
`ds-ai-hub`: `ab`, `abm`, `am`, `ao` или `site`. Product записывается в
`snapshot.context.product`; это не визуальный фильтр интерфейса.
Если импортированный manual source всё ещё содержит старый идентификатор вроде
`alfa-business`, он появляется в отдельной группе **Legacy / IDs из контракта**.
Это позволяет проверить текущий контракт, но одновременно делает необходимость
явного mapping на `ab` видимой.

### Переход между вкладками Figma

Editor автоматически сохраняет активный каталог и текущую ручную ревизию в
локальной сессии плагина. Если нужный instance находится в соседней вкладке или
другом Figma-файле:

1. Сохраните правило или паспорт обычной кнопкой формы.
2. Перейдите в нужную вкладку и запустите там тот же development-плагин.
3. Editor восстановит компонент, manual rules, выбранный Product, variants и
   modes. Повторно импортировать пакет не требуется.
4. Выделите instance и нажмите **Проверить**.

Сессия — runtime-копия, а не второй source of truth. В ней не сохраняются PNG,
snapshot выбранного документа и compiled JSON. Поэтому evidence всегда снимается
заново в активном Figma-файле, а Predicate Engine получает контракт, только что
скомпилированный из текущего `contract.manual.json` в памяти Editor.

Если manual source был изменён во время построения reference baseline, Editor
отбрасывает устаревший ответ и автоматически повторяет проверку с актуальным
`manualSourceHash`.

Результат **Не применяется** означает, что правило осознанно не запускалось —
например, оно ограничено Product `ab`, а для проверки выбран `ao`. Это не
«Пройдено» и не недостаток evidence. В деталях Editor показывает выбранный
контекст и область правила: например, `Альфа-Онлайн (ao) ≠ Альфа-Бизнес (ab)`.
Если не выполнено условие variant или mode, значения подписываются как
**Сценарий сейчас** и **Правило применяется при**, а не как ошибочное
«сейчас → должно быть».

На вкладке **Проверка** справа находится единый инспектор: сведения о контракте,
Product, режим, ожидаемые параметры, переходные состояния, результаты и действия
**Проверить** / **Скачать отчёт**. Верхняя строка сценария и нижняя панель
компиляции остаются только в **Каталоге**. Блок **Observed facts** в режиме
проверки скрыт: он нужен для выбора capability при authoring, но не для чтения
результата проверки.

### Строка Preview scenario

Здесь показываются имя компонента, его библиотека, текущая revision и
переключатели доступных component properties. После живого рендера здесь также
появляются найденные variable collections и их modes.

Если Athena package содержит несколько платформенных main-компонентов одного
семейства, первым отображается переключатель **Компонент** — например
`[D] Button · desktop` и `[M] Button · mobile-web`. Preview и componentKey
меняются, но при импорте одного semantic manual source все representations
редактируют тот же `contract.manual.json`.

Кнопка **Паспорт** открывает поля всего компонента: identity, semantics,
representations, semantic API, documentation refs, examples, normative
decisions и generation profiles. В разделе «Когда не использовать» каждая
Condition заполняется отдельной карточкой: само условие обязательно, а component ID
альтернативы можно оставить пустым. Остальные большие структурированные блоки
редактируются как JSON и валидируются перед сохранением.

Изменение variant или mode запускает новый preview и новый factual snapshot.

### Левая колонка — Anatomy

Это фактическое дерево импортированного экземпляра:

- `C` — component или instance;
- `T` — text;
- `F` — frame или group;
- `S` — slot;
- `L` — другой слой.

Нажатие на строку выбирает область действия будущего правила. Поиск сверху
фильтрует дерево по имени, пути и semantic role.

Цветной индикатор справа показывает устойчивость semantic target:

| Цвет | Состояние | Значение |
|---|---|---|
| Зелёный | `resolved` | Цель однозначно найдена. |
| Жёлтый | `ambiguous` | Найдено несколько подходящих узлов. |
| Жёлтый | `unknown` | Для сопоставления пока недостаточно evidence. |
| Красный | `missing` | Цель была в manual source, но отсутствует в текущем экземпляре. |

Перед переводом правила в `reviewed` желательно устранить `ambiguous` и
`missing`.

### Общая цветовая легенда

| Область интерфейса | Цвет | Значение |
|---|---|---|
| Индикатор в верхней панели | Серый | Плагин ждёт импорт или действие. |
| Индикатор в верхней панели | Синий, пульсирующий | Идёт импорт или построение preview. |
| Индикатор в верхней панели | Зелёный | Manual source валиден и готов. |
| Индикатор в верхней панели | Жёлтый | Есть предупреждения или контракт требует внимания. |
| Левая граница Typed constraint | Чёрная | Permission `forbidden`. Constraint заменён проверкой baseline. |
| Левая граница Typed constraint | Зелёная | Permission `allowed`. Это policy-only правило. |
| Левая граница Typed constraint | Красная | Permission `constrained`. Constraint будет скомпилирован в RuleIR. |
| Результат Test | Зелёный | `compliant`. Проверка пройдена. |
| Результат Test | Красный | `violation`. Найдено нарушение. |
| Результат Test | Жёлтый | `human-review` или `not-evaluable`. Evidence недостаточно. |
| Всплывающее сообщение | Красная граница | Ошибка операции или validation. |
| Всплывающее сообщение | Жёлтая граница | Некритичное предупреждение. |

Цвет всегда дублируется текстом или статусом — он не является единственным
носителем информации.

### Центральная колонка — Evidence

Здесь находится PNG-preview фактического экземпляра. Он создаётся на временной
служебной странице Figma. После получения изображения и snapshot временный
instance и страница удаляются даже при ошибке.

Под preview находится **Observed facts** выбранного узла. Нажатие на свойство
переносит его путь в поле Capability справа. Это основной способ создавать
правило без знания JSON.

#### Работа с текстовым узлом

Да, текстовый узел можно выбрать в Anatomy. Он обозначен буквой `T`.

После выбора в Observed facts доступны, в зависимости от evidence:

- `text.characters` — фактическое текстовое значение;
- `text.fontSize`;
- `text.fontName.family` и `text.fontName.style`;
- `text.lineHeight`;
- `text.letterSpacing`;
- `text.case`;
- typography и fill facts из раздела `appearance`.

Чтобы проверить конкретное значение текста:

1. Выберите узел `Label` или другой TEXT-узел.
2. Нажмите `text.characters` в Observed facts.
3. Выберите permission **С условиями**.
4. Выберите constraint **Допустимые значения**.
5. Введите разрешённые строки через запятую.

Для Button чаще правильнее регулировать не внутренний `text.characters`, а
публичное `component-property.*`, через которое меняется label. Тогда target
может оставаться текстовым узлом, capability описывает публичное свойство, а
control path выставляется в `Host property`. Прямой контроль
`text.characters` используйте только тогда, когда контракт действительно
разрешает или запрещает редактировать внутренний TEXT-слой.

### Правая колонка — Author

Здесь создаётся ручное нормативное правило. Колонка прокручивается независимо
от preview.

Правая колонка имеет два отдельных состояния:

1. **Правила компонента** — просмотр всех существующих правил и быстрых
   действий. Нажмите карточку правила, чтобы открыть её, либо `+`, чтобы создать
   новое.
2. **Новое правило / Изменение правила** — детальная форма. Стрелка в заголовке
   возвращает к списку, не удаляя preview и snapshot.

В состоянии просмотра доступно быстрое действие **Защитить внутреннее
устройство**. Оно создаёт или обновляет два обычных manual rules: запрет
`auto-layout@1` и `visual-style@1` на корневом target вместе со всеми потомками.

Публичные component properties настраиваются через те же карточки правил и
детальную форму. Отдельного параллельного редактора публичных свойств нет.

Быстрые действия не создают отдельный формат и не изменяют generated facts.
Они записывают те же canonical manual rules, которые видны в детальном
редакторе и компилируются общим compiler core.

В карточке правила отображаются permission, status, semantic target, scope и
**Variants**. Значение **Все** означает действие на все варианты; для
ограниченного правила показывается сохранённая комбинация, например
`View=Primary · Size=56`.

Нажатие на карточку загружает правило в детальную форму, но не перестраивает и
не удаляет preview. Метка **Preview закреплён** означает, что текущие
изображение, anatomy и snapshot остаются контекстом редактирования. После
сохранения Editor возвращается к списку правил. Для проверки переключитесь на
вкладку **Проверка**, выделите instance и нажмите **Проверить**.

Если поверх открытого компонента импортировать `contract.manual.json` того же
семейства, библиотеки и платформы, Editor заменит только manual-слой и сохранит
текущий preview/snapshot. В новой сессии один `contract.manual.json` сам по себе
не содержит изображения: сначала возьмите instance из Figma либо импортируйте
Athena package с variant evidence.

### Нижняя строка — Test & compile

Здесь отображаются validation status, число созданных RuleIR и предупреждения.
Кнопка **Compiled JSON** открывает только read-only представление результата.

## 4. Создание правила

### Шаг 1. Выберите target

Нажмите компонент, слот или слой в Anatomy. Editor создаст либо переиспользует
semantic target. Контракт не опирается только на нестабильный `nodeId`: также
сохраняются semantic role, path, lineage, имя и structural fingerprint.

### Шаг 2. Выберите группу и свойства

Самый безопасный способ — нажать фактическое свойство в **Observed facts**.

Типовые capability:

```text
appearance.fill
appearance.stroke
appearance.opacity
appearance.radius
layout.mode
layout.itemSpacing
layout.padding.top
component-property.View
visibility
```

Сначала выберите **Группу**:

- **Одно свойство** — обычное capability выбирается в поле **Свойство слоя**, а
  публичное свойство экземпляра — отдельно в поле **Component Property**;
- **Заливка** — paint-значение и локальный paint style;
- **Обводка** — paint, style, толщина, выравнивание и dash pattern;
- **Автолейаут** — направление, отступы, интервалы, выравнивание и sizing;
- **Скругление** — радиусы;
- **Эффекты** — эффекты и effect style;
- **Внешний вид** — единая группа основных визуальных параметров:
  заливка, обводка, прозрачность, скругление и эффекты.

В UI версии групп не показываются. В manual source они по-прежнему сохраняются
как `fill@1`, `stroke@1` или `visual-style@1`: суффикс фиксирует состав группы и
не даёт будущему обновлению незаметно изменить уже созданный контракт.

Суффиксы Figma вида `#4:8` у Component Property также скрыты в UI. Это
внутренние идентификаторы, которыми Figma различает свойства с одинаковыми
именами; Editor сохраняет их в контракте, но показывает автору только понятное
имя — например **Hint**.

После выбора семантической группы Editor показывает её свойства чек-листом.
Изначально выбраны все свойства; ненужные можно снять. В manual source
сохраняется `capabilitySelection`, а compiler создаёт RuleIR только для
выбранного подмножества. Пустую группу сохранить нельзя.

**Внешний вид** является полноценной рабочей группой. Используйте её,
когда правило должно защищать визуальный образ слоя целиком. Отдельные группы
заливки, обводки, скругления и эффектов удобнее, когда требуется более узкое
правило.

Группа — это стабильный набор capabilities. Она не означает «все свойства
компонента навсегда».

В поле **Область действия** задаётся, к каким слоям применяется правило:

- **Только выбранный слой** — проверяется semantic target;
- **Только вложенные слои (без выбранного)** — проверяются потомки semantic target,
  но не сам target. Например, sizing внутренних слоёв защищён отдельно от допустимых
  режимов ширины корня. Поддерживаются propertyDomain и baseline-сравнения
  propertyForbidden; структурные/dependency constraints здесь не поддерживаются.
  Политика component-owned продолжает исключать область доказанной pinned-зависимости;
  отсутствие достаточных данных даёт неполную проверку, не разрешение изменения.
- **Слой и все его потомки** — проверяются target и все вложенные слои. Этот
  scope подходит, например, для запрета автолейаута или внешнего вида во всём
  внутреннем устройстве компонента.

При групповом запрете Editor проверяет capability только на тех слоях, где оно
присутствует в effective baseline. Отсутствующее у данного типа слоя свойство
не считается нарушением. При этом явное значение `null` считается
присутствующим и нормативным: например, `stroke: null` означает, что обводки
быть не должно. Если такое свойство удалить или заменить ненулевым значением,
проверка вернёт violation.

### Шаг 3. Назначьте permission

#### Запрещено

Свойство нельзя менять вручную. Для свойства слоя compiler автоматически
создаёт проверку на совпадение с effective baseline текущего variant/mode.
Для boolean **Component Property** (например `Hint`) запрет означает, что
property должна быть выключена: допустимо только `false`. Это выражает именно
«Hint использовать нельзя», а не только «Hint нельзя менять».

Для полностью запрещающего правила выставьте:

| Поле | Значение |
|---|---|
| Target | Компонент, слот или слой, свойство которого защищается. |
| Область действия | **Только выбранный слой** либо **Слой и все его потомки**. |
| Capability | Запрещаемое свойство или версия группы свойств. |
| Permission | **Запрещено**. |
| Control path | Не заполняется и блокируется интерфейсом. |
| Typed constraint | Для слоя не заполняется; compiler использует effective baseline. Для boolean Component Property Editor сохраняет допустимое значение `false`. |
| Severity | Обычно `error`; `warning`, если отклонение временно допустимо. |
| Status | `draft` во время настройки, затем `reviewed`. |
| Owner | Команда-владелец правила. |
| Rationale | Обязательно для `reviewed`: почему изменение запрещено. |
| Remediation intent | Необязательно; например `restore-effective-baseline`. |

Запрещающее правило действует на изменение capability независимо от способа,
поэтому у него нет разрешённого control path.

#### Разрешено

Изменение допустимо через заданный control path. Это policy-only запись: она
попадает в `customizationPolicy`, но не создаёт бессмысленный RuleIR.

Для разрешающего правила используйте:

| Поле | Что вводить |
|---|---|
| Target | Область, которую разрешено настраивать. |
| Область действия | **Только выбранный слой** либо **Слой и все его потомки**. |
| Capability | Конкретное свойство или версионированная группа. |
| Permission | **Разрешено**. |
| Control path | Реальный публичный способ управления: `Direct`, `Host property`, `Slot API` и т. п. |
| Property / port | Заполняется для выбранного пути; для `Direct` можно оставить пустым. |
| Другие пути запрещены | Включить, если разрешён только указанный путь. |
| Typed constraint | Не заполняется и блокируется интерфейсом. |
| Severity | Рекомендуется `info`: это metadata политики, а не severity violation. |
| Status | `draft` до подтверждения, затем `reviewed`. |
| Owner | Владелец разрешения, обычно `design-system-authors`. |
| Rationale | Для `reviewed` обязательно объяснить, зачем customization разрешён. |
| Remediation intent | Обычно оставить пустым: нарушение не создаётся. |

Applicability всё равно важно: разрешение может действовать для всех variants
либо только для текущей комбинации.

#### С условиями

Изменение разрешено только при выполнении typed constraint. Именно этот режим
используется для разрешённых доменов значений, диапазонов, количества,
отношений и token bindings.

### Шаг 4. Укажите control path

#### Условия сравнения неактивных свойств (0.2.31)

В **Applicability** доступны два списка: «Толщина обводки · когда сравнивать» и
«Gap · когда сравнивать». По умолчанию дополнительных условий нет: старые правила
не меняют смысл при обновлении плагина.

- Для `appearance.strokeWeight` можно сравнивать только при наличии stroke
  в экземпляре **или** независимом эталоне. Добавленная/удалённая обводка не скрывается;
  даже hidden/transparent stroke считается существующей привязкой.
- Для `layout.itemSpacing` можно сравнивать, когда хотя бы в одном состоянии
  H/V auto layout содержит ≥2 видимых не-absolute детей. Один ребёнок не образует gap.
- Эти условия действуют только на указанные сравнения с baseline, не на всю группу.
  Выбор условия для правила, в котором такого сравнения нет, блокируется валидацией.
- При доказанной неактивности результат — **«Не применяется»** с объяснением.
  Если фактов недостаточно — **неполная проверка**, а не разрешение изменения.

Условия сохраняются в `contract.manual.json → rules[].propertyApplicability`.
Для Spinner загрузите пакет **r5**: он включает все шесть правил r4 и свежие sources.
Один перезапуск плагина не добавляет условия в старый manual. После изменения политики
пересмотрите статус reviewed и перепроверьте нужные variants/modes.

Permission отвечает на вопрос «можно ли менять», а control path — «как именно
этим разрешено управлять».

| Control path | Когда использовать |
|---|---|
| `Direct` | Свойство разрешено менять непосредственно на target. |
| `Host property` | Управление идёт через component property родительского компонента. |
| `Nested property` | Используется публичное свойство вложенного instance. |
| `Slot API` | Управление происходит через содержимое или конфигурацию слота. |
| `Variable binding` | Значение задаётся binding на разрешённую variable. |
| `Inherited port` | Владение передаётся наружу через локальный control port компонента. |

Если включено **Другие пути запрещены**, указанный путь считается единственным
допустимым способом изменения.

`Inherited port` не превращает внешнего владельца в часть ComponentContract.
Плагин создаёт только локальный порт. Кто именно подключён к нему, позже
определяет PatternContract.

### Шаг 5. Задайте typed constraint

Typed constraint применяется для permission **С условиями**.

| Тип | Назначение |
|---|---|
| Допустимые значения | Значение должно входить в заданный список. |
| Наличие / отсутствие | Target должен присутствовать или отсутствовать. |
| Совпадает с baseline | Свойство не должно отличаться от effective baseline. |
| Количество | Число элементов с semantic role должно попасть в диапазон. |
| Порядок | Прямые дочерние элементы должны идти в указанной последовательности. |
| Связь элементов | Проверяет parent/ancestor/child/descendant/before/after/adjacent. |
| Token binding | Требует binding и, при необходимости, один из разрешённых token IDs. |
| Layout constraint | Проверяет точное значение или числовой диапазон. |

Значения в списке разделяются запятыми. `true`, `false`, `null` и числа
сохраняются как типизированные значения, а не строки.

### Шаг 6. Настройте applicability

- **Variants → Все варианты** — правило действует на любую комбинацию variant
  properties. Ниже показаны реальные свойства и значения из Athena evidence.
  Можно выбрать несколько значений одного свойства: между ними действует `OR`,
  между разными свойствами — `AND`. Кнопка **Только preview: …** отмечает точную
  комбинацию открытого экземпляра, а не абстрактное значение «Текущий».
- **Modes → Все modes** — правило не зависит от Figma Variables. После live
  preview Editor показывает коллекции переменных и их настоящие modes. Можно
  выбрать несколько modes в каждой коллекции; compiler сохраняет связь
  `collectionId → modeIds`, поэтому `Dark` из разных коллекций не смешивается.
- **Products → Все** — правило не ограничено продуктом. Для ограниченного
  правила раскройте список и выберите один или несколько продуктов из
  `ds-ai-hub/products`: Альфа-Бизнес (`ab`), Альфа-Бизнес Мобайл (`abm`),
  Альфа-Мобайл (`am`), Альфа-Онлайн (`ao`) или Сайт (`site`). Редкий новый либо
  legacy product ID можно указать отдельно, не меняя формат контракта.
- **Channels → Все** — правило не ограничено каналом продукта. Словарь совпадает
  с product manifests `ds-ai-hub`: **Desktop** (`desktop`), **Mobile Web**
  (`mobileweb`) и **Adaptive** (`adaptive`). `B2B` и `Universal` относятся к
  классификации каталогов Athena и здесь больше не используются.

Пункт **Все** означает отсутствие фильтра по этой оси. Сохранённые значения,
которых нет в текущем evidence или встроенном словаре, Editor не удаляет: он
показывает их как legacy/custom до явной миграции mapping.

### Шаг 7. Заполните служебные поля

- **Severity** — `error`, `warning` или `info`.
- **Status** — `draft`, `reviewed` или `deprecated`.
- **Owner** — владелец ручного правила.
- **Rationale** — почему правило существует.
- **Remediation intent** — безопасное намерение исправления, а не произвольный
  исполняемый код.

Для `reviewed` обязательно заполнить Rationale. Пока правило находится в
`draft`, весь compiled contract также остаётся `draft`.

Нажмите **Сохранить правило**. Editor вернёт вас к основному списку правил, не
удаляя текущий preview.

## 5. Четыре базовых сценария

### Запретить ручной radius

1. Выберите корневой слой компонента.
2. Capability: `appearance.radius`.
3. Permission: **Запрещено**.
4. Control path и typed constraint не заполняйте — они будут заблокированы.
5. Severity: `error`.
6. Status: сначала `draft`, после проверки `reviewed`.
7. Опишите rationale и сохраните правило.

Apollo будет сравнивать radius с effective baseline текущего состояния.

### Разрешить изменение текста Button

1. Выберите текстовый слой Button.
2. Нажмите соответствующий observed fact либо выберите публичное
   `component-property.*`.
3. Permission: **Разрешено**.
4. Выберите `Host property`, если текст должен меняться через property Button.
5. Введите имя property в поле **Property / port**.
6. Severity: `info`.
7. Оставьте Remediation intent пустым.
8. Заполните rationale и сохраните правило.

Такое правило формирует customization policy и не создаёт violation само по
себе.

### Ограничить opacity набором значений

1. Выберите нужную поверхность.
2. Capability: `appearance.opacity`.
3. Permission: **С условиями**.
4. Constraint: **Допустимые значения**.
5. Значения: `1, 0.64`.
6. Сохраните правило.

### Передать управление layout владельцу композиции

1. Выберите слот или внутренний layout-контейнер.
2. Capability или группа: `Auto layout @1`.
3. Выберите подходящий permission.
4. Control path: `Inherited port`.
5. Введите стабильный id, например `port.body-layout`.
6. Оставьте **Другие пути запрещены** включённым.
7. Сохраните правило.

Editor автоматически создаст component-local control port. Имя внешнего
компонента-владельца здесь указывать не нужно.

## 6. Проверка instance в документе

Переключитесь в режим **Проверка** и выберите Product. Без явного Product запуск
заблокирован: иначе невозможно надёжно определить применимость product-scoped
rules. Все параметры, результаты и действия находятся в правом инспекторе.

Preview остаётся визуальным контекстом для настройки контракта, но отдельно не
проверяется: рабочая проверка всегда снимает актуальные факты выделенного instance.
Так результат нельзя случайно принять за проверку реального макета.

Живой preview по импорту требует Athena evidence с `figma.variants.variantKeys`.
Key Component Set нельзя передавать в `importComponentByKeyAsync`: Figma API
импортирует только конкретный variant component key. Поэтому при импорте одного
`contract.manual.json` Editor не делает ошибочный сетевой запрос и предлагает
проверить выбранный instance. Manual rules при этом загружаются полностью.

### Проверить выделенный instance

Эта проверка предназначена для настоящего экземпляра на странице Figma:

1. Импортируйте `contract.manual.json` либо ZIP с контрактом.
2. Переключитесь на вкладку **Проверка** и выберите Product.
3. Создайте или найдите на странице instance того же компонента.
4. Внесите тестовое изменение, например поменяйте запрещённый padding или
   добавьте stroke.
5. Оставьте выделенным ровно один instance.
6. В правой панели нажмите **Проверить**.

Editor не заменяет открытый контракт и не принимает проверяемый instance за
эталон. Он создаёт на временной служебной странице чистый reference instance
того же variant, применяет к нему mode и только разрешённые публичные component
properties, после чего сравнивает фактический instance с этим effective
baseline. Служебная страница и reference instance удаляются в `finally`.

Проверка отклоняется с `Component mismatch`, если ни key варианта выделенного
instance, ни key его родительского Component Set не принадлежат открытому
контракту. Поэтому контракт с identity на `[D] Button` Component Set применим ко
всем его вариантам, даже если у каждого варианта собственный component key.

После проверки центральный preview и Anatomy показывают именно выделенный
instance. Узлы с нарушениями подсвечиваются; нажатие на итоговый chip переводит
фокус на первый узел соответствующей категории, не создавая нового manual
target.

Если rule содержит `scope.product`, Predicate Engine применяет его только при
совпадении с выбранным Product. При другом или отсутствующем Product результат
этого правила — `not-applicable`.

Проверка использует тот же Predicate Engine, что Apollo, и возвращает:

- `compliant` — правило выполнено;
- `violation` — правило нарушено;
- `human-review` — evidence неизвестно или недостаточно;
- `not-applicable` — правило не действует в текущем сценарии.

Нижняя панель показывает только компактную сводку русскими статусами:
**Нарушения**, **Требуют проверки**, **Пройдено**. Нажмите на любую карточку,
чтобы открыть подробную диагностику. Для каждого результата показываются:

- конкретный узел и полный путь в Anatomy;
- capability и severity;
- человеческое объяснение результата;
- rationale исходного manual-правила;
- сравнение **Сейчас → Должно быть** из исходного Apollo trace;
- кнопка **Показать в Anatomy**.

В Anatomy теперь два разных индикатора. Маленькая точка справа относится только
к устойчивости semantic target: зелёная — resolved, жёлтая — ambiguous/unknown,
красная — missing, серая — для слоя ещё нет manual target. Отдельный badge перед
точкой показывает результат Test: красное число — количество нарушений,
жёлтое — проверки, требующие внимания, зелёная галочка — проверки пройдены.

Permission `allowed` остаётся в customization policy и поэтому не создаёт
отдельную строку проверки Predicate Engine.

Во время локального Test правила со статусом `draft` временно получают authority
`active` в тестовой копии compiled contract. Это позволяет проверить правило до
ревью. Канонический manual source и экспортируемый compiled contract не
изменяются и сохраняют статус `draft`. Правила со статусом `deprecated` локально
не активируются.

Если кнопка выключена, значит snapshot ещё не получен. Проверьте componentKey,
доступ Figma-файла к библиотеке и дождитесь окончания preview.

Для проверки выделенного instance кнопка также выключена, если на странице не
выделен ровно один `INSTANCE`.

### Минимальный acceptance-набор для Button

| Изменение instance | Ожидаемый результат |
|---|---|
| Ничего не менять | Нет `violation`. |
| Изменить запрещённый padding | `violation` на соответствующем узле. |
| Добавить stroke при baseline `null` | `violation`; `null` означает, что обводки быть не должно. |
| Изменить label через разрешённое component property | Нет нарушения от этого изменения. |
| Заменить addon через разрешённое instance-swap property | Нет нарушения от этого изменения. |
| Выделить другой компонент | `Component mismatch`, проверка не запускается. |

### Использование того же контура после генерации

Генератор не должен иметь отдельный валидатор. После создания instance он
передаёт factual snapshot в тот же `evaluateCompiledContract` и принимает
результат только при отсутствии блокирующих `violation`/`human-review`.
Customization policy используется до генерации для ограничения допустимых
component properties, а compiled RuleIR — после генерации для проверки
фактического дерева. Сам генератор и автоматический repair в Editor MVP пока не
входят; готовый instance можно проверить кнопкой выше.

## 7. Экспорт

Нажмите **Экспорт**.

С Editor 0.2.74 имя сохраняет регистр названия семейства. Desktop-пакет
CorporateContent скачивается как `CorporateContent.component-contract.zip`,
mobile-web — как `CorporateContent.mobile-web.component-contract.zip`.
Если паспорт объявляет несколько платформ, в имени перечисляется весь scope,
например `Button.desktop.mobile-web.component-contract.zip`; переключение
preview не меняет имя общего пакета. Старые архивы импортируются как прежде.

Архив содержит:

```text
contract.manual.json
compiled/component-contract.v2.json
coverage.json
validation-report.json
```

### contract.manual.json

Канонический редактируемый источник. Для продолжения работы импортируйте именно
его либо ZIP, в котором он находится.

### compiled/component-contract.v2.json

Детерминированный runtime artifact. Его нельзя использовать как ручной source
of truth.

### coverage.json

Показывает число policy rules, policy-only правил, созданных RuleIR,
неисполняемых правил и покрытие по типам constraints.

### validation-report.json

Содержит ошибки и предупреждения схемы. Экспорт возможен и для draft, но готовым
к Apollo следует считать контракт без validation errors и с reviewed rules.

## 8. Рекомендуемый первый прогон

### Сессия 1 — Button

1. Импортируйте пакет Button.
2. Оставьте desktop Button и один простой variant.
3. Создайте три правила:
   - изменение текста разрешено через host property;
   - ручной radius запрещён;
   - View ограничен известным доменом component property.
4. Проверьте каждый вариант.
5. Экспортируйте ZIP.

Пакет Button содержит много variants. На первом прогоне не пытайтесь описать их
все: задача — подтвердить модель permission/control path/constraint.

### Сессия 2 — CorporateContent

1. Перезапустите Editor и импортируйте пакет CorporateContent.
2. Выберите корень `[D] CorporateContent`.
3. Создайте правила:
   - manual fill запрещён;
   - grid/padding управляется через variable binding;
   - содержимое Body разрешено через slot API;
   - layout Body передаётся через component-local inherited port.
4. Запустите проверку.
5. Экспортируйте отдельный ZIP.

## 9. Ограничения текущего MVP

- Одна component family за сессию.
- При пакете с несколькими контрактами Editor пока автоматически выбирает
  основной desktop-компонент.
- Нет Git publish и синхронизации обратно в Athena.
- Нет AI rule generation.
- Нет редактора произвольного RuleIR.
- Нет page-level и pattern-level правил.
- Нет code mapping editor.
- Нет встроенного генератора и automatic repair; Editor предоставляет тот же
  snapshot + Predicate Engine контур для post-generation проверки.
- Импорт compiled v2 не восстанавливает manual rules.
- Mode preview работает, но mode-scoped conditions пока рекомендуется оставлять
  `all` до отдельной parity-проверки.

## 10. Если что-то не работает

### Пустой preview

- Проверьте наличие `componentKey` в пакете.
- Убедитесь, что текущий Figma-аккаунт имеет доступ к библиотеке компонента.
- Если contract не содержит variant keys, переключитесь в **Проверка**, выделите
  instance в документе и нажмите **Проверить**.
- Если Figma не ответила за 20 секунд, loader остановится автоматически.
  Authoring по импортированным facts останется доступен; смените variant или
  повторите импорт, чтобы запросить preview снова.

### У TEXT-узла не видно `text.characters`

- Убедитесь, что выбран именно узел с маркером `T`, а не содержащий его frame.
- `text.characters` теперь показывается первым в Observed facts.
- После обновления сборки полностью перезапустите development-плагин в Figma:
  открытое окно не подменяет уже загруженный `dist/code.js` автоматически.

### Пустая Anatomy

Пакеты Editor до 0.2.65 сохраняли manual и compiled, но не исходные Athena JSON.
Editor 0.2.65 восстанавливает из compiled компактную анатомию и варианты. Для
полного дерева со свойствами слоёв импортируйте старый ZIP **вместе с исходными
Athena JSON за одно действие**. Затем скачайте новый ZIP: он включает оба слоя
данных, и повторный импорт восстановит полную анатомию и ручные правила.
Если ни structure signature, ни достоверной структуры compiled нет, живой preview
заполнит дерево фактической структурой instance; это не доказанный baseline.

### Validation error после сохранения

Проверьте target, capability, constraint values, rationale для reviewed-правила
и существование inherited port.

### Target стал ambiguous или missing

Athena regeneration либо другой variant изменил структуру. Не создавайте новое
правило автоматически: сначала выберите корректный слой и подтвердите semantic
target вручную.
